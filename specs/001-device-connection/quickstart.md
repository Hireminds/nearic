# Проверка подключения и OTA

Нужны физический ESP32-S3-BOX-3B, USB-C с передачей данных, телефон, две сети,
VPS с реализацией [контракта](contracts/device-service.md), плагин Codex и CLI
на удалённом хосте. Комплект подключения не должен содержать общих секретов.

## Сборка

В активированной среде ESP-IDF v5.5.6 из корня репозитория:

```bash
idf.py -C firmware set-target esp32s3
idf.py -C firmware build
```

При выпуске задайте версию до подписания образа и сверьте её с полем `App version`
в выводе `image_info`.

```bash
idf.py -C firmware -D PROJECT_VER=0.1.1 build
esptool.py --chip esp32s3 image_info --version 2 firmware/build/nearic.bin
```

Зафиксируйте версию, размеры и `firmware/build/flasher_args.json`. Издатель
подписывает `firmware/build/nearic.bin` ключом выпуска RSA-3072, включая
первую USB-сборку. Для подписания используют `espsecure.py sign_data --version 2`
и отдельно проверяют результат `espsecure.py verify_signature --version 2`
с публичным ключом. BOX сверяет подпись OTA с публичным ключом из подписи
текущего образа. Размер и SHA-256 для публикации рассчитывают по итоговому
подписанному файлу. В комплекте USB-установки по адресу приложения из
`flasher_args.json` должен быть подписанный образ. После установки образа
оставьте `nearic_cfg` отдельным от двух слотов приложения. [Руководство Espressif по подписанию](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32s3/security/secure-boot-v2.html#signed-app-verification-without-hardware-secure-boot)

### Диагностика подписи и отката

Тестовое приложение ESP-IDF v5.5.6 на ESP-Emulator 1.2.0 загрузилось из `ota_0`
с пустым `otadata`, записало подписанный образ в `ota_1` и подтвердило его
после первого запуска. Перезапуск до подтверждения и явный отказ проверки
вернули `ota_0`. В обоих случаях сохранилось тестовое значение из `nearic_cfg`.
Чужая подпись, повреждённый блок подписи и обрезанный образ были отклонены до
смены загрузочного слота.

Тестовое приложение читает образ из отдельного раздела эмулятора и использует
программную криптографию, стек 8 КиБ и буфер 1 КиБ вне стека. На BOX дополнительно
проверяются HTTPS-загрузка, рабочие настройки, сохранение привязки, фактический
запас стека при проверке образа и USB-восстановление.

### Запись и активация в прошивке

[Модуль обновления](../../firmware/main/update.c) принимает поток подписанного
файла и проверяет его полный размер, SHA-256, версию приложения и подпись
ESP-IDF. Граница подписанного образа проверяется по фактически полученному
размеру. Это важно при повторной записи слота, в котором осталась подпись
от предыдущего файла. При обрыве или ошибке текущий загрузочный слот сохраняется.

Вызов записи оставляет готовый образ в свободном слоте. Контроллер сервиса
проверяет, что настройка Wi-Fi и операция завершены, вызывает активацию и
инициирует перезапуск. Активация сохраняет попытку перед выбором загрузочного
слота. Аппаратная проверка всего цикла выполняется по T012.

Полная прошивка собрана на ESP-IDF v5.5.6. Тот же модуль прошёл 12 сценариев
на ESP-Emulator 1.2.0, включая запуск и подтверждение нового образа, оба вида
отката с сохранением NVS, короткое чтение, лишние данные, неверную версию,
хеш и подпись. Обрезанный файл отклонён даже при наличии его старой подписи
во flash.

### Восстановление исхода OTA

[Журнал](../../firmware/main/update_journal.c) хранит в `nearic_cfg` исходный
слот, цель и SHA-256 образа. При старте прошивка проверяет, что было записано
в `otadata`. Если питание пропало до выбора слота, запись попытки освобождается
для повтора. После подтверждения нового образа попытка закрывается. При возврате
в исходный слот с `ABORTED` или `INVALID` для цели журнал выдаёт хеш отката.

До подтверждения исхода сервисом новые образы ждут. Прошивка принимает
подтверждение с совпавшим хешем из авторизованного ответа. Последний сбойный
хеш переживает перезапуск и блокирует повторное предложение того же файла.

В ESP-Emulator 1.2.0 на ESP-IDF v5.5.6 проверены сбой записи в NVS, перезапуск
после записи перед выбором слота, повтор активации после потери её результата,
оба вида отката и повтор отчёта после перезапуска. Подтверждение чужого хеша
сохраняет отчёт. После совпадающего подтверждения журнальная запись переживает
перезапуск и повторное предложение отклоняется до чтения образа.

### HTTPS-загрузка подписанного файла

[Загрузчик](../../firmware/main/update_download.c) принимает путь из предложения
и отправляет GET на HTTPS-адрес из доверенной конфигурации BOX. Он передаёт
токен устройства в `Authorization`, сверяет цепочку, имя и срок сертификата и
отклоняет редиректы. Контроллер запускает загрузку после получения проверенного
UTC. Ответ `200` поступает в модуль записи потоком. При наличии `Content-Length`
проверяется размер, а для chunked проверяется завершение потока. Сбой ответа до
первых байтов оставляет свободный слот без записи. Код HTTP доступен контроллеру,
чтобы отдельно обработать запрет на выдачу файла.

На ESP-IDF v5.5.6 и ESP-Emulator 1.2.0 проверены `401`, `403`, редирект,
недопустимый адрес, неверный сертификат и обрыв. При завершённом скачивании
образ с `Content-Length` и образ в chunked-передаче проходят одну проверку
подписи. После отдельной активации BOX сохранил Wi-Fi и сообщил `0.1.1`
тестовому сервису.

### Обновление из обмена с сервисом

[Обработчик `/sync`](../../firmware/main/service_sync.c) передаёт сохранённый
отчёт об откате и принимает подтверждение только с SHA-256 отправленного отчёта.
После получения и проверки образа следующий успешный `/sync` должен подтвердить
то же предложение. При незавершённой операции или занятой настройке Wi-Fi
активация откладывается. Успешная активация возвращает признак готовности к
перезапуску. Владелец цикла устройства сериализует разрешение обновления с
началом настройки Wi-Fi и инициирует перезапуск.

Рабочий запуск цикла получает адрес сервиса, токен BOX и подтверждённый UTC
после первичного подключения. Для приёмки требуется прогон всего цикла через
VPS на физическом BOX.

На ESP-Emulator 1.2.0 выполнены 16 реальных HTTPS-обменов с тестовым сервисом.
Предложенный `0.1.1` отложен при активной команде и запрете локального
контроллера. После его отката сервис сохранил отчёт и оборвал ответ. BOX повторил
отчёт после перезапуска, пропустил несовпадающее подтверждение и принял
совпадающее. Сервис зафиксировал одну запись об откате, одну загрузку сбойного
файла и одну загрузку следующего образа. После подтверждения запуска BOX сообщил
`0.1.2` с прежним Wi-Fi.

### Первичное получение доступа BOX

[Источник времени](../../firmware/main/clock_sync.c) использует настроенные
адрес и открытый ключ Roughtime. После подключения Wi-Fi он формирует запрос
со случайным nonce, проверяет подписи и окно делегирования, ответ на этот запрос,
радиус времени и длительность обмена. Только затем он устанавливает UTC для
обычной проверки срока сертификата HTTPS. Рабочий адрес, ключ и предельные
значения входят в конфигурацию пилота.

[Модуль первичного доступа](../../firmware/main/device_bootstrap.c) получает
проверенный адрес Nearic, UTC и индивидуальный допуск из 32 байт от контроллера
установки. При работающем Wi-Fi он сохраняет ключ P‑256 в `nearic_cfg` перед
первым HTTPS-запросом. Сервис присылает одноразовый challenge, и BOX подписывает
его сохранённым ключом. Только проверенный ответ с `deviceId` и `accessToken`
записывается в локальный доступ. После перезапуска контроллер читает доступ из
NVS и передаёт токен в `/sync`.

При потере ответа после выдачи BOX запрашивает новый challenge с прежним ключом.
Ключ хранится отдельной записью от токена. Для пилота требуются рабочая выдача
допуска при первой USB-установке и настроенный источник проверенного UTC.

На ESP-Emulator 1.2.0 с подписанным тестовым образом проверены новая выдача
`201` и восстановление `200` после потери ответа. BOX отклонил изменённое
кодирование токена, снова получил исходный доступ и выполнил авторизованный
`/sync` после перезапуска. В обоих прогонах тестовый сервис сохранил одну
запись BOX и вернул состояние `pending` с кодом регистрации.

В проверке холодного старта ESP-Emulator получил UTC от Roughenough 2.2.0 до
первой выдачи и после перезапусков. Проверка TLS при сброшенных часах дала отказ.
Модуль времени отклонил ответ на прежний запрос, изменённую подпись, неверный
корневой ключ, слишком большой радиус и запоздавший ответ. После принятия UTC
оба сценария выдачи дошли до `/sync` с кодом регистрации. Сборка использовала
тестовый допуск и тестовые ключи.

## Первый запуск с телефона

Сценарии ниже относятся к целевой реализации первой итерации.

1. Установить подписанную сборку по USB и подать питание на BOX. Начать с
   устройства без сохранённой сети и регистрации. Зафиксировать версию на экране.
2. По подсказке BOX присоединиться с телефона к его настройочной сети и открыть
   локальную страницу. Выбрать домашнюю сеть 2,4 ГГц. Проверить повтор после
   неверного пароля и затем ввести верный. После успеха временная сеть закрывается.
   Повторить на iOS и Android. Проверить ручное открытие страницы, возврат
   к активной сессии после обрыва и запуск новой сессии после истечения.
3. При подключённом Wi-Fi и недоступном VPS проверить, что BOX ждёт сервис.
   Восстановить доступ и вернуть телефон в сеть с интернетом. Навести камеру
   телефона на QR-код с физического экрана BOX и открыть страницу добавления BOX.
   Повторить переход, введя короткий адрес с экрана вручную. В обоих случаях
   должна открыться одна HTTPS-страница Nearic. Войти и отдельно подтвердить
   одноразовый код с экрана.
   Проверить появление колонки в аккаунте, отклонение просроченного и использованного
   кодов и получение нового кода по запросу на BOX. При обновлении истёкшего
   кода потерять ответ и восстановить связь. BOX должен прочитать уже выданный
   новый код с его оставшимся временем действия.

## Сквозной прогон

### Проверка адреса Codex

Диагностический вызов локального MCP в Codex CLI 0.162.0 подтвердил совпадение
`params._meta.threadId` с ID тестового разговора. После `codex exec resume`
инструмент получил тот же ID. Аргументы инструмента были пустыми. Проверка
касалась доставки поля от CLI в stdio MCP. Для приёмки остаются Desktop,
проверка источника контекста на границе сервиса, вход из SSH через браузер
другого компьютера и полный прогон с BOX.

В локальной проверке схемы обмена тот же CLI вызвал диагностический MCP из двух
тестовых разговоров. Имитатор BOX опрашивал `POST /device/v1/sync` каждые две
секунды. Стенд подтвердил свежий результат, отсутствие ответа за десять секунд,
изоляцию позднего результата старого запроса и отказ прежнему разговору после
переключения. Адреса и привязки заданы тестовым стендом. Для приёмки повторяем
проверки на развёрнутом сервисе с настоящей авторизацией и физическим BOX.

### Привязка, статус и OTA

1. Для зарегистрированного BOX пройти авторизацию в Desktop и выбрать колонку
   из существующего разговора A. Из A запросить
   состояние. Сверить ID запроса и версию BOX. Убрать Wi-Fi и поймать тайм-аут.
2. В CLI на удалённом хосте авторизоваться через ссылку, выбрать существующий B
   и перепривязать BOX. Проверить отказ для A, живой ответ из B, перезапуск BOX
   и сохранение регистрации и привязки.
3. На экране BOX начать смену Wi-Fi. Неудачная попытка или отмена сохраняет прежнюю
   сеть. После успешной смены на другую сеть из B снова приходит живой ответ.
   Отдельно проверить смену сети на другой канал, перезапуск до сохранения
   новой конфигурации и отзыв доступа агента. Во время ожидания IP от первой
   новой сети отменить попытку и начать другую. Проверить, что сохраняется только
   профиль успешной попытки. Повторить смену для прежнего SSID с новым паролем.
   На тестовой плате прервать питание во время смены профиля. До полной записи
   нового слота BOX загружает прежний профиль, после записи — новый. Проверить,
   что настройка с телефона остаётся доступной после восстановления связи.
4. Опубликовать совместимый подписанный образ. Дождаться автоматического
   получения и загрузки, из B получить новую версию. Повторить с обрывом
   скачивания и с согласованным тестовым образом для проверки отката.
   После отката проверить живой ответ из B со старой версией и убедиться,
   что сервис больше не предлагает этот образ тому же BOX. При потере
   подтверждения результата проверка повторяется после перезапуска BOX.
5. Восстановить устройство по USB и отдельно зафиксировать результат.
   Записать ревизию платы, версии сборок, клиентов и сервиса. Исключить
   коды, токены и настройки Wi-Fi из отчёта.
