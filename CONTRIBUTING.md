# Участие в разработке

Nearic использует GitHub Spec Kit с интеграцией Codex и доменными Living Spec.
Начните с [принципов](.specify/memory/constitution.md), [инструкций агенту](AGENTS.md)
и [карты процесса](docs/process/spec-kit.md). Draft — контекст обсуждения, не разрешение на код.

## Установка инструмента

Нужны Git, Bash, Python 3.11+, [uv](https://docs.astral.sh/uv/getting-started/installation/)
и [Codex CLI](https://developers.openai.com/codex/cli/), авторизованный обычным способом.
Скрипты поддерживают Linux/macOS; на Windows используйте WSL.

После клонирования репозитория, из его корня:

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@v1.4.3
specify version
specify check
specify integration status --json
specify workflow list
```

Если executable не найден, добавьте каталог инструментов uv в PATH по его инструкции.
Официальные скиллы, шаблоны, скрипты и три workflow уже находятся в репозитории;
повторный `specify init --force` не требуется. Установка не меняет модель и аккаунт Codex.

## Полный workflow в чате

Сначала согласуйте скоуп и существенные решения. Обычные этапы агент проходит самостоятельно;
следующая итерация согласовывается отдельно. Для полного процесса есть три проектных скилла:

```text
$hireminds-feature Выполни согласованное изменение; укажи затронутый домен.
$hireminds-bugfix Исправь описанное отклонение от ожидаемого поведения.
$hireminds-assess Исследуй идею и подготовь обоснованное решение.
```

Это сообщения в текущем чате. Входной скилл читает выбранный YAML-workflow и его включённые
overlays, затем применяет официальные скиллы этапов. Собственной копии порядка в нём нет.
[Правила выполнения в чате](docs/process/chat-workflows.md) описывают обработку команд,
gate и циклов. Это работа модели, не программная гарантия runner.

Можно также попросить обычным языком применить подходящий входной скилл.
Для конкретного этапа остаются доступны официальные навыки, например `$speckit-analyze`.

При изменении существующего домена назовите его директорию. Агент сначала читает текущий
контракт и сохраняет незатронутые требования. Смена Git-ветки не выбирает активную спеку.
В `specs/` находятся доменные контракты приложения; для установки инструмента отдельная
продуктовая спека не создаётся.

## Автоматизированные запуски

Тот же источник порядка можно исполнять через CLI:

```bash
specify workflow run speckit --input spec="Описание новой согласованной возможности"
specify workflow run bugfix --input report="Симптом и воспроизведение" --input slug=short-bug-name
specify workflow run assess --input idea="Описание идеи" --input slug=short-idea-name
specify workflow status
specify workflow resume RUN_ID
```

Полный runner speckit начинает новый комплект. Для развития существующей доменной спеки
используйте входной скилл в чате. CLI вызывает Codex отдельно; необходимые договорённости
должны быть записаны в материалах задачи, а не только в истории разговора.

Встроенные gate останавливают runner. Ведущий агент читает результат и продолжает обычные
этапы внутри согласованного скоупа; новый существенный выбор выносит владельцу.
Не выставляйте verdict до чтения результата. Синтаксис продолжения — в
[карте процесса](docs/process/spec-kit.md).

## Рабочие материалы

Официальные скиллы bug и assess создают временные отчёты в `.specify/bugs/` и
`.specify/assessments/`. Эти пути исключены из Git. Итоговые внутренние материалы ведущий
агент сохраняет в приватной проектной системе; автоматической синхронизации с Linear нет.
Решение исследования само по себе не разрешает реализацию.

## Проверка и поставка

```bash
python3 -m unittest discover -s tests/process -v
specify integration status --json
specify workflow resolve speckit
specify workflow resolve bugfix
specify workflow resolve assess
git diff --check
```

Тесты оркестрации используют заглушку Codex и не отправляют запросы модели.
Проверка скилла также требует просмотра его инструкций, ссылок и соответствия выбранному
YAML; программные тесты runner не доказывают качество интерпретации моделью.
Успешные проверки, merge, аппаратная проверка и приёмка — отдельные результаты.

PR содержит ссылки на применимые продуктовые спеки или диагностику, затронутые решения,
фактические проверки и ограничения. Для изменения инструмента или документации достаточно
согласованного задания и проверок; отдельная спека установки не требуется.
Скоуп и отчёт владельцу хранятся в приватной проектной системе.

## Слияние и версии прошивки

Изменения в `main` проходят через pull request. Для squash merge нужны
успешная сборка ESP32-S3 и тесты Spec Kit, а также закрытые обсуждения в PR.

Версии прошивки следуют SemVer. При подготовке выпуска обновите `PROJECT_VER`
в `firmware/CMakeLists.txt` через PR. Для принятой версии используйте тег вида
`v0.1.0`, для кандидата — `v0.1.0-rc.1`. Создавайте тег на соответствующем
коммите из `main`. Перед созданием тега сверьте поле `App version` собранного
образа с версией, которую собираетесь выпустить. CI повторит сравнение с тегом.
Опубликованный тег закреплён за своим коммитом.

Релиз публикуется после приёмки на BOX. В релиз входят подписанный образ,
контрольная сумма и инструкция установки. Порядок проверки образа, подписи и
USB-восстановления описан в [руководстве по сборке и проверке](specs/001-device-connection/quickstart.md).
